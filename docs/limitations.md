# Limitations

GoalPort **1.0.0-rc.1** is a **Stable V1 RC** (release candidate). It has not closed Stable V1. This page describes current source unless it explicitly names the previously built RC package.

## Distribution and platform

- **The desktop distribution targets Windows x64.** Linux Core has a developer entry, not a packaged Linux desktop.
- Linux Core can run native Codex through the Unix command client ([Linux development](linux-development.md)). Connections are isolated with bounded waits. This does not establish native Claude/Grok or Windows desktop acceptance. Socket ownership and peer checks remain in force; a foreign or unidentifiable stale endpoint is never silently replaced.
- **The Windows Pi workspace check has one bounded real acceptance.** A packaged build ran one real Codex turn and one real Pi check, including closing the window while Pi ran and returning to the result. It did not cover an attached session on the final build, Stop during a real run, or native OS input. While a check runs on another goal, the composer names it; there is no Open current work strip on the desktop.
- **No downloadable release.** You build the package from source ([building](building.md)).
- **Unsigned package.** Windows may warn before running it.
- **Tauri** is a bounded regression target, not a second product.

## Data

- **Profile reuse depends on data compatibility.** Current source can reopen compatible data and offers supported imports with backups; unknown or newer formats remain refused ([profile continuity](profile-continuity.md)). Previously built RC packages keep their original build-bound behavior.
- **Moved profiles are refused.** So are profiles from the earlier path identity format. Nothing is rewritten.
- **Workspace matching is conservative.** Distinct folders that collapse to the same comparison key are refused.

## Runtimes

- **Admission status differs per Runtime.** Runtime support is shown as Available or Limited, according to the current capability projection. Codex is partial, Claude Code is partially admitted and Grok is admitted. Each ruling applies to a specific recorded build; a package built from current source has not been re-admitted ([runtime integration](runtimes.md#support-status)).
- **Claude session resume and explicit close work for the recorded Claude build.** Resume is spawn-only: the stored session id is verified on the first send and nothing is replayed. A resume whose verification fails retires its process and leaves a dormant successor that offers a deterministic retry ([safety](safety.md#stop-and-held-responsibility)). The window can still close while work continues; Stop retains unresolved responsibility where required.
- **CLI version changes are not detected.** Newer Runtime CLI versions may behave differently from the recorded ones.
- **Environment-failure detection is a proven-signature closed set.** When a Codex planning or check turn's own JSONL tool events all fail with a sandbox-helper signature (`helper_unknown_error`, `Failed to create unified exec process`, `sandbox failed`, proven by the captured diagnostic turn in `goal-runs/goalport-pr26-blockers-codex-diag/`), the harness is named as unable to run its tools on this machine. What happens next depends on authorization. Inside a harness access scope, a proven environment failure hands that role to another authorized harness — a new turn with its own grant, never a replay of the failed one — so the round can still finish on the harnesses you allowed; the same handoff applies to the other continuable failure classes (a harness that is not installed, stopped without text, or did not finish, and usage or sign-in failures on the harness's own side), and only when GoalPort knows whether the failed turn was actually sent. Without a scope, the round keeps the legacy early stop: at most one plan and one check, no automatic continuation, and no third turn. Signatures not in that set are not classified as environment failures, the stderr fallback carries the same limit, Claude turns have no structured tool events and rely on that fallback only, and the signature set is not re-derived when the CLI changes.
- **A harness that cannot run on this machine is remembered, with its evidence, until you clear it.** When a turn proves the machine could not run a harness's tools, GoalPort stores the timestamp and the failure detail (the same proven signatures, capped in length) beside the send ledger and shows the harness as "Blocked on this machine since …" in Harness access; it stays unused for plan and check turns. You can clear the mark at any time with **Use again**, and it also clears on evidence: for Codex, one completed tool call that did not fail proves the tools ran again, while for harnesses without structured tool events a successful turn is the strongest evidence available and clears on that alone. There is no timed re-probe and no automatic re-check — an automatic retry would spend a model turn against your subscription to ask a question the evidence already answered.
- **Ordinary harness access is authorized per window and is never written to disk.** The set of allowed harnesses and the model-turn budget live in the main process of the running window (the window shows a mirror); quitting GoalPort ends the authorization, and **Stop allowing** ends it immediately, after which a new send needs a fresh authorization. The main process alone holds the budget and refuses turns past it; each turn inside the scope writes and consumes the same per-command send-authorization grant a hand-written authorization would, so the audited send path does not change. The read scope covers planning, checking and independent verification; workspace changes require a separate explicit write authorization with its own budget and pinned workspace (below). At authorize time every instance must be discovered and signed in with a subscription — an API-key (paid) login is refused entry, so automatic recovery can never drift onto a billed API. What the scope cannot see: it records the sign-in type as it was at authorize time, so a later change of CLI credentials on your side is not bound to it, and nothing re-checks membership until you authorize again.
- **The Scenario Runtime is synthetic.** Its checks never count as native Runtime evidence.

## Coordination execution evidence

- **Read consent is not permission to edit.** For a goal sent without choosing a single Runtime, the existing Harness access section selects read members and a read-turn budget. Workspace changes are separately default-OFF, with their own selected members and 1–8 write-turn budget. For ordinary Sends, both grants are per-window/session-bound, never persisted, and **Stop allowing** revokes both. Execution spends a write turn; planning, checking and verification spend read turns. A checked plan with no write consent stops without editing.
- **Writes are launched only against the authorized workspace.** Main-process authority checks the captured scope generation, execution role, write membership, workspace root equality and workspaceWrite command pairing before granting a launch. A changed root, revoked scope or exhausted budget refuses the next launch. This binds the launch; it is not physical filesystem confinement. Actual file restriction depends on the installed harness CLI's sandbox mode. Real CLI flags/models and confinement are **unverified in this round**; the local offline peers check only the fixed disposable fixture root/marker and intercepted mode.
- **“Changes verified” is conditional harness evidence, not a built-in test runner.** Only a completed writer followed by a different read-only harness whose final line is `VERDICT: verified` can produce it. GoalPort preserves the execution and verification reports in history, but does not generally run or validate workspace tests itself. The local real-app acceptance uses closed offline processes: the writer really repairs a broken Node fixture after its original tests fail, and a separate read-only Node checker reads it and reruns the unchanged tests. This is real filesystem/subprocess evidence, **not independent-model judgment**. A writer that exits unsuccessfully stops with its partial report and may leave edits; no automatic retry, audit takeover or rollback is implied. Inspect the workspace before a fresh send.
- **Implementation, preview and native acceptance are different evidence.** Unit/component checks cover consent, authoritative dual counters, role pairing, terminal partial writes and record round trips. Synthetic built-UI previews cover three widths, history display and save-failure honesty. The reproducible `pnpm acceptance:execute-native --out <fresh run evidence directory>` driver uses the actual Electron main/preload, built renderer, Core and two sentinel-controlled offline stub processes in WSL/Linux, through normal DOM permission/Send/Close controls; no grants, ledger or history are manually seeded. Its b1/b2/b3 records prove four-role repair/verification, exactly two read-only turns/no edits, and exactly three turns/actual partial edit/failed checks/no audit respectively. The continuation driver `pnpm acceptance:feedback-native --out <fresh run evidence directory>` proves the one in-window repair end to end: its C1 record covers one authorization and one Send running both four-role chains (eight turns, six read/two write) after a genuinely failed unchanged check produced a completed critique, and its C2 record proves the four-read-turn default stops with an explained budget refusal and no fifth turn. The plan-revision driver `pnpm acceptance:plan-revision-native --out <fresh run evidence directory>` proves the one pre-write plan revision end to end: its PR1 record covers one authorization and one Send running the rejected plan/check plus the revised four-role chain (six turns, five read/one write) after a separate read-only plan checker produced a completed critique of a specific missing plan requirement, PR2 proves the four-read-turn default stops with an explained budget refusal and no third turn, PR3 proves a second plan-check `revise` is terminal with no writer, and PR4 proves the explicitly admitted background job runs the same revision after the desktop closes. The plan critique and revised-review approval are closed offline fixture behaviors and separate read-only Node processes, **not independent-model judgment**. CDP input is not OS keyboard/mouse. Native Windows packaged EXE, OS/IME/close behavior, real vendor CLI/model/auth/help/probes and live quota/resource readiness are **not run**, not inferred from these checks. The desktop suite retains nine named baseline failures and platform-specific skips.
- **One automatic repair may follow a completed verification, inside the same open window.** When a four-role round finishes and its independent execution audit ends `VERDICT: revise`, GoalPort may run exactly one further checked four-role chain in the same Send, without a new authorization: the original scope generation, memberships, workspace root and remaining budgets are reused, the audit's actual findings are carried into the corrective prompts, command identities are fresh (`repair-1`), and the harnesses that failed in the first chain stay excluded. Before the first corrective turn the app re-checks the live scope and records the completed first round with an honest unconfirmed repair intent, so an interrupted repair leaves a readable, non-retryable record. The repair needs three remaining model turns and one write turn; if the budget is short, the stop says so and no turns are added or borrowed. A refused or cancelled corrective launch, an unknown dispatch, a writer failure, or a second `revise` is terminal — the first round's reports stay readable under **Before automatic repair**, and the goal never becomes silently resendable because a later pass proved it sent nothing. This does not run after a *plan*-review revision, after a failed or unconfirmed round, from history selection, after reopening the app, or after the window closes for an ordinary Send. The separate explicit background job below can own the same bounded repair without a window.
- **One automatic plan revision may precede any write, inside the same open window.** When a scoped, write-consented Send's independent **plan check** (not its execution audit) ends `VERDICT: revise` and no writer or auditor was launched, GoalPort may run exactly one revised chain in the same Send, without a new authorization: the same scope generation, memberships, workspace root and remaining budgets are reused, the rejected plan and the actual critique are carried into the revised prompts as `priorPlan`/`priorReview`, and command identities are fresh (`plan-revise-1`). Before the first revised turn the app re-checks the live scope and records the rejected round with an honest unconfirmed revision intent. The revised chain needs three remaining model turns and one write turn (five read turns fund the healthy path; the four-read-turn default stops with an explained budget refusal and no third turn). A refused or cancelled revised launch, an unknown dispatch, or a **second plan-check `revise`** is terminal — the rejected pass's reports stay readable under **Before plan revision**, and the goal never becomes silently resendable. A later in-Send execution-audit `revise` may still start the unchanged one repair above, under the revised identity namespace, with both retained histories surviving; plan revisions inside that corrective chain remain terminal. The explicitly admitted background job can own the same bounded revision after the desktop closes.
- **This is a bounded four-role round plus at most one in-window plan revision and one in-window repair, not an autonomous goal service.** A general budget-bound feedback/revise loop beyond those two one-shot boundaries, automatic resource-restoration resume and automatic worker/system-crash execution resume remain gaps. Ordinary Sends remain window-bound; the legacy Core/session background semantics above do not establish four-role continuation. **Use again** clears blocked-harness health and, from a finished result, opens a new draft of the same goal. Nothing is sent until Send, and the failed round is not replayed. Real resource readiness and provider-side budget behavior still need validation. Local b1 success does not accept the whole goal.

## Safety and recovery

- **Residual execution after a Claude Code Stop is not proven quiescent.** Release is evidence-based only: a confirmed cancel needs a quiet workspace, and an unconfirmed Stop additionally needs the bound Runtime observed gone with its recorded identity plus a durable record that no execution was ever admitted ([safety](safety.md#stop-and-held-responsibility)).
- **An unconfirmed Stop whose process ever admitted execution stays held.** There is no evidence path to release such a hold; continue in a new isolated workspace instead. Holds recorded before the admission ledger existed also stay held.
- **Stop release's observation residuals (honest unknowns).** Release never concludes from absence: it requires every descendant snapshotted at Stop time to be identity-confirmed dead, except identity-matched session helpers sealed before a confirmed Stop, readable workspace writers absent, and two equal whole-folder fingerprints. That exemption does not apply to an unconfirmed Stop, to a process introduced by the current turn, or to a survivor from an earlier turn. The fingerprint is an uncapped stat of every file and directory the walk can read. Beyond that observation sit documented residuals: a non-descendant process you left writing the workspace yourself is not this turn's residual execution; a descendant re-parented before the Stop was pressed, or spawned in the window between the Stop-time snapshot and the CLI's death, is caught by the fingerprint layers if it writes the workspace but its liveness is not separately proven; an entry the walk cannot read holds the release as unknown. Any workspace write from a sudo'd (foreign-UID) descendant still lands in the fingerprint layers, but its process liveness is only recorded while the CLI lives.
- **Revocation was not blocking in one historical check.** A packaged-GUI check found the next send was not blocked after a revoke (SEC-02 in [S/R/D acceptance](reference/acceptance-srd.md)).
- **Outbound effects are not exactly-once.** A missing receipt after an external effect stays unknown.
- **Reconnecting the window is not recovery of native execution.** A restarted Core does not re-attach to earlier Runtime processes.
- **No sandbox.** `READ_ONLY` is a declaration, not an operating-system sandbox.
- **Supervised launches may lose Core.** When GoalPort starts inside a job object that refuses breakaway (some terminals and CI runners), the supervisor can end Core when the job ends.

## Local pipe security

The Core pipe accepts only the Windows user account that runs Core and rejects remote clients ([architecture](architecture.md#processes)). What that does not cover:

- **Processes of the same user are trusted.** Any process running as that user can open the pipe, including lower-integrity processes (the pipe has no integrity label). Such a process can also hold Core's single serving connection and stall the window's requests.
- **Administrators and SYSTEM keep access.** Their privileges reach the pipe regardless of its access list.
- **A pipe name taken while Core is down blocks Core.** Core refuses to start on a name another process created, and at startup the window refuses to attach to it, so launching GoalPort fails (a denial of service). A name taken while the window is already attached is covered by the snapshot-poll limitation below.
- **Snapshot polls are not re-verified on every poll.** The window checks the pipe server with `goalport-core pipe-peer` before attaching, before every other request and after any connection failure. If Core stops and another process takes its pipe name between two polls, the window can show that process's data until the next command or connection failure triggers a check, which then refuses. The check and the connection are separate steps.
- **A busy Core delays commands.** A command that needs a check waits at most 120 seconds from when it is issued for a successful check, including checks queued ahead of it and a repeated check after a connection failure. It is then refused rather than sent unchecked. The command's own response limit is another 120 seconds, so a command can wait about 240 seconds in total.
- **The window's pipe client does not limit impersonation.** Node's named-pipe client connects without a security quality-of-service setting. A process holding `SeImpersonatePrivilege` that took over the pipe name in the gap above could impersonate the window's user on that connection. Core's Rust client does set identification-only impersonation; that flag is checked statically, not by a live test.
- **An open connection keeps a crashed Core's process object referenced, but a confirmed exit no longer blocks restart.** A same-user client can still hold a handle to a Core that has already terminated. Core now treats that confirmed-exited process as ended, so a new Core may start on the same database and pipe name. A prior Core that is still executing, or whose identity cannot be confirmed, still refuses the second start. The open connection does not prove that Runtime tools or descendants have finished, and it does not release held or uncertain responsibility.
- **Denial is tested with a restricted token, not a second Windows account.** The different-account squatting case is covered by the Windows API's first-instance rule and by `pipe-peer`'s access-list check.
- **Remote rejection was tested only through local SMB loopback.** The tests open the pipe as `\\127.0.0.1\pipe\...` on the same machine. Clients on other machines rely on the documented `PIPE_REJECT_REMOTE_CLIENTS` behavior and were not tested from another host.
- **Other clients do not check the server.** The `src-tauri` host and the developer tools in `scripts/connected` do not run `pipe-peer`. Neither does Electron started in the legacy isolated test mode without a data profile (`GOALPORT_REQUIRE_ISOLATED` without `--data-dir` or `--test-profile`); there the window performs no `pipe-peer` check. Process scans that match `goalport-core.exe` and the pipe name on the command line can also match a short-lived `pipe-peer` process.

## Window and UI

- **Controls adapt to the window width.** Runtime selection, Send, Stop and permission cards stay in the main conversation; navigation becomes a dismissible drawer at narrow widths. Desktop-native IME and operating-system close behavior still need Windows validation.
- **Timestamps are formatted for the local display.** Raw committed timestamps remain in the stored events.
- **Desktop notifications are not verified.** They use AUMID `GoalPort.Desktop` without a Start Menu shortcut, and visible toasts were not captured as evidence.

## Explicit one-goal background coordination (C2)

- **Keep working after closing is a separate, default-OFF decision on Send.** It admits only this goal to an app-independent worker. Read members/turn limits and workspace-change members/root/write limit are separately selected; background consent never permits edits. Ordinary Sends still use window-owned access. Closing the window after that choice leaves the job running without asking again.
- **One live worker owns one profile admission and the original scope.** Reopening observes that same job without resending, authorizing again, or replacing either budget. While outstanding, it blocks competing GoalPort coordination/native execution, not Core Stop, permission, held-responsibility or recovery controls. Native close receipts remain a separate contract.
- **Stop allowing denies subsequent turns, not past effects.** A currently admitted turn may settle and its reports remain. Missing/unreachable control is not proof that the worker or tools stopped. Held responsibility, native work or unavailable Core projection blocks each new role and repair, even when the selected workspace is blank.
- **Closing the window is not crash recovery.** Worker or system death keeps the admission, command claims and unconfirmed pending facts. GoalPort does not restart the worker, replay the turn, or rebuild the budget. If the job is not live, you can leave it and open a new send: the old turn stays unconfirmed, the same request is not admitted again, and a new send does not prove that tools from the interrupted turn have stopped. Ordinary history and fresh drafts restore neither background nor write consent.
- **Acceptance is bounded Linux offline evidence.** `pnpm acceptance:background-native` uses actual Electron/Core and sentinel-shadowed fixture processes to prove BG1 close-before-writer/one-repair/same-live-return, BG2 revoked access/current-turn settlement, and BG3 interrupted owner/no replacement. It does not accept real model judgment, real vendor CLI behavior, Windows packaged lifetime or full GAH. Packaged-default coordination admission is unchanged.
