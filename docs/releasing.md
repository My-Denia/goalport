# Releasing

This page describes how a verified Windows RC package becomes a downloadable
GitHub Release candidate, and the gates a candidate must clear before an
owner publishes it. It does not itself publish anything: creating a Git tag,
a GitHub Release, or uploading a public asset are all separate, explicit
owner actions this tooling never performs.

See [signing](signing.md) for the code-signing decision, and
[limitations](limitations.md) for what the RC does not do yet.

## Format: portable ZIP, no installer

The first downloadable RC ships as a portable Windows x64 ZIP, not an
installer. GoalPort today is a self-contained, movable package folder
([building](building.md)); an installer would add install-path, upgrade,
uninstall, elevation, shortcut, registry and signing-of-an-installer
questions this RC does not need to answer yet. Revisit this once there is
real signal that users need an installer, not before.

## From a verified package to a release candidate

Beyond [building](building.md)'s prerequisites, `release:bundle` needs
**PowerShell 7 (`pwsh`)** on `PATH` for its Authenticode inventory step (it
still uses Windows PowerShell's `Compress-Archive` to build the ZIP itself)
— see [signing](signing.md) for why Windows PowerShell 5.1 is not used for
the Authenticode check specifically.

```powershell
pnpm install --frozen-lockfile
pnpm electron:package --out artifacts/release-candidates/build
pnpm electron:verify --package artifacts/release-candidates/build/GoalPort-win32-x64
pnpm release:bundle --package artifacts/release-candidates/build/GoalPort-win32-x64 --out artifacts/release-candidates/candidate
pnpm release:verify-bundle --bundle artifacts/release-candidates/candidate --work artifacts/release-candidates/candidate-verify
```

`release:bundle` (`scripts/release/build-release-bundle.mjs`) refuses to run
unless:

- the package's own `package-manifest.json` verifies (`electron:verify` would
  pass);
- the live source tree is clean (`git status` shows nothing and there are no
  new untracked build inputs);
- the live source revision and source-tree digest exactly match what the
  package was built from (a package built from a different or older checkout
  is refused, not silently accepted);
- the repository's `package.json` version and the package's embedded version
  agree;
- the destination directory does not already exist (a candidate is never
  overwritten; build a new directory instead).

It never modifies the package directory's own file inventory. Legal files
(`GOALPORT-LICENSE.txt`, `THIRD_PARTY_NOTICES.txt`, `README-RELEASE.txt`) are
added at an outer wrapper level, sibling to an untouched copy of the package,
so the package's own `package-manifest.json` stays exactly verifiable on its
own and the release bundle's `release-manifest.json` separately accounts for
everything the ZIP actually contains. The ZIP extracts to:

```
GoalPort-<version>-windows-x64/
  GOALPORT-LICENSE.txt
  THIRD_PARTY_NOTICES.txt
  README-RELEASE.txt
  GoalPort-win32-x64/
    GoalPort.exe            <- run this
    LICENSE                 (Electron's own, unmodified)
    LICENSES.chromium.html  (Chromium's own, unmodified)
    package-manifest.json
    resources/...
```

`release:bundle` also writes `release-manifest.json` (the release-level
identity and integrity contract) and `SHA256SUMS.txt` (covering the ZIP and
the manifest itself) next to the ZIP. None of these three files claim a
bit-for-bit reproducible build; they claim exact provenance (which source
commit, which package) and integrity (which bytes), which is what this stage
requires.

`release:verify-bundle` (`scripts/release/verify-release-bundle.mjs`) proves
the candidate end to end rather than checking that a ZIP file exists:

1. every entry in `SHA256SUMS.txt` matches the file on disk;
2. `release-manifest.json`'s recorded ZIP hash and size match the ZIP;
3. the ZIP extracts into a brand-new directory (never reused);
4. the extracted `GoalPort-win32-x64` independently passes
   `electron:verify`'s own checks;
5. the extracted package passes normal smoke, synthetic smoke and
   early-cleanup exactly as a freshly built package would
   (`scripts/desktop/smoke.mjs --normal`, `scripts/desktop/smoke.mjs`,
   `scripts/desktop/verify-early-cleanup.mjs`).

A release candidate is never built from a historical `artifacts/electron-rc`
output, a `goal-runs` evidence folder, or an existing user profile. It is
always built from a fresh `pnpm electron:package` against the current, clean
checkout.

## Third-party notices

`release/THIRD_PARTY_NOTICES.txt` is generated by
`pnpm release:third-party-notices`
(`scripts/release/generate-third-party-notices.mjs`) from the live
dependency graph, scoped to what actually ships:

- the normal (non-dev, non-build) Rust dependency closure of
  `goalport-core`/`goalport-core-launcher` for `x86_64-pc-windows-msvc`,
  minus proc-macro crates and anything reachable only through one (those run
  as host-side compiler plugins and contribute no bytes to the binary);
- the vendored SQLite amalgamation compiled in via rusqlite's `bundled`
  feature (public domain, quoted from its own header, not asserted from
  memory);
- the npm runtime dependency closure that Vite actually bundles into
  `resources/app.asar` (`react`, `react-dom`, `scheduler`, `@tauri-apps/api`
  today).

It intentionally excludes Electron's own bundled Chromium/Node/V8 stack:
that ships its own `LICENSE` and `LICENSES.chromium.html` at the package
root, unmodified, and this repository does not regenerate or replace them.

`scripts/release/third-party-notices.test.mjs` fails if the checked-in file
drifts from what the current lockfiles would generate, so a dependency bump
that changes the shipped closure has to be a conscious, reviewable diff, not
a silent gap.

Two shipped npm packages in the current graph (`@tauri-apps/api`'s installed
package, and any future one like it) do not carry a bundled license file;
the generated notices flag this explicitly as a verify-before-release item
rather than fabricating license text.

## Version and tag

- Version: `1.0.0-rc.1`. Channel: `Stable V1 RC`, not Stable V1.
- Planned tag: `v1.0.0-rc.1`, pointing at the exact commit the published
  candidate was built from. This tooling does not create it.
- A published tag is never moved and never reused for different bytes. If
  `v1.0.0-rc.1` needs a fix after publishing, the next binary release is
  `v1.0.0-rc.2` (or later), not a second `v1.0.0-rc.1`.
- A profile is bound to the Core binary hash of the build that created it
  ([local data](local-data.md)); release notes must keep saying so.

## GitHub Release contract (for the owner, when the time comes)

- Create the tag at the exact approved commit, then a GitHub prerelease
  (`prerelease: true`), as a **draft** first.
- Attach the ZIP, `SHA256SUMS.txt` and `release-manifest.json` to the draft,
  and re-verify their hashes from the uploaded copies before publishing —
  not just the local files.
- Publish only after that explicit review. This repository's tooling does
  not create tags or Releases, draft or otherwise.
- **Immutable releases**: GitHub's immutable-releases setting only affects
  Releases published after it is turned on. If it is going to be used at
  all, turn it on before publishing the first real Release, not after.
  Check Settings before tagging; this round does not change repository
  settings.
- **Artifact attestations**: public repositories can generate build
  provenance attestations for release assets via GitHub's official
  `actions/attest-build-provenance` action (pin to a full commit SHA,
  minimal permissions, run only for real release assets), verifiable by
  downloaders with `gh attestation verify`. This is worth doing for the
  first real Release; it is not done in this round, since it publishes to a
  public transparency log and should happen for a real asset, not a
  readiness-stage rehearsal.

## What this tooling deliberately does not do

- Create a Git tag.
- Create a GitHub Release, draft or published.
- Upload a public release asset.
- Sign anything (see [signing](signing.md)).
- Claim a runtime is admitted based on this packaging or verification work
  ([native validation gate](signing.md#native-runtime-exact-build-gate)).
